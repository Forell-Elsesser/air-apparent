## What the project is

ASCE 7-10 horizontal MWFRS wind loads for one rectangular data-center building, assigned to an open
ETABS model over the COM API. Pipeline: YAML config -> adapter (`FakeAdapter` or unverified
`ComEtabsAdapter`) -> categorize every shell/frame/joint -> pressures -> `LoadPlan` (patterns, cases,
assignments, W1-W4 combinations) -> apply -> read-back verify. `WindSession` in `workflow.py`
orchestrates; core modules only import `models.py`. Tkinter GUI in `ui.py`. The initial PR was
Copilot-generated; `docs/limitations.md` and `docs/engineering_basis.md` are candid and accurate.

from workbook), W_Ecc torsion and W1-W4 (provisional), 16 psf minimum check (approximate), equipment
overturning (omitted).

### Code vs spec vs sample model: they diverge

`docs/spec_categorization.md` (22 lines) defines shell groups by five distinctions: wind direction,
element type (wall / parapet / mech screen or equipment), loading type (windward / leeward /
mechanical), side relative to centre or grid line, and level. Workflow: import grids, stories and
shell unique names; for each direction, pick the windward side and find shells on that grid line.
**This is grid-based.** The current `categorization/rules.py` is envelope-based (bounding rectangle
of dominant wall lines, 0.25 ft tolerance, 98 % edge coverage) and never reads grids. The
`ModelSnapshot` dataclass has no grid field and the COM adapter does not read grids.

The sample model (`Test Model.e2k`) shows how the engineers actually did it:

| Aspect | Code today | Sample model / spec |
| --- | --- | --- |
| Units | ft, psf, kip; adapter switches to kip-ft | `UNITS "KIP" "IN" "F"` (inches) |
| Categorization | geometric envelope | one group per load pattern (`W_Wall_+X`, `W_Parapet_-Y`, ...) whose members are exactly the loaded objects; see "Decisions" below about the other groups |
| Shell pressure direction | local axis 3 with sign from `assignment_sign` | `AREALOAD ... TYPE "UNIFF" DIR "X"` / `"Y"` (global direction; sign independent of local axes; no `LOCALAXESANGLE` on any area) |
| Mechanical patterns | 2 reversible (`W_Mech_X/Y`) + 4 signed cases | 4 patterns `W_Mech_+X/-X/+Y/-Y`, 20 patterns total |
| Equipment loads | joint forces on 4 support joints | frame point loads (`TYPE "POINTF"`, `RDIST 1`) on beams at story `MECH`; **no point-object loads at all** |
| Platform loads | uniform frame line load | `UNIFF` and `TRAPF` frame loads on story `MECH` |
| Combinations | `W1_+X` linear, `W1_ENV` envelope, `W2_+X_+E` | `W_+X` linear (Wall+Parapet+PH+Mech), `W1` envelope of the four; `W2_+X_+T`; `W3_+X_+Y`; `W4_+X_+Y_+Tx_+Ty`; nested combos reference `LOADCOMBO "W_+X"` |

## Later in the session: categorization design (afternoon)

The repo received a seven-story Test Model (`examples/Test Model.$et` is its text export; the
old `.e2k` is the four-story version), a user guide, and a refactored combinations package.
Lint and tests still green. Brainstorming for the categorization module concluded with these
decisions by James:

- Rule-based categorization from **story lines (Story API)** and **grid lines (interactive
  tables)**. Grid lines are a convenience, not a requirement.
- **Exterior wall faces are declared in YAML as segments** (line, range, outside direction), not
  inferred by outline tracing.
- Only `W_*` groups are read, compared and written. The tool writes back **exactly the sixteen
  per-pattern `W_*` groups**, not the finer five-distinction groups.

Findings that drove the design (all verified against the `$et` with throwaway scripts in the
session scratchpad, not kept):

- New stories sit at feature tops: Parapet_1 65.083 ft, Mech 70.708, Penthouse 75.167,
  Parapet_2 76.917 (base -0.833, L2 31.5, R 60.083). Geometry did not move; every upper object
  is still *labelled* story R with a z-offset, so story labels are unusable and level must be
  computed from z against story elevations.
- Rule "level = story band containing the shell's top; element type from level; shell on a
  declared exterior segment" reproduces `W_Parapet` 695/695 and `W_PH` 28/28 exactly, and
  `W_Wall` 568/568 once the exterior is declared. The 99 perimeter-line shells the engineers did
  not load are 83 interior walls behind four 11 ft bump-outs (x 21-306 and 2621-2900 in, beyond
  J and E) and 16 panels of the grid 28.5 west wall, which is a cut line (building continues).

### Live read-only check (late afternoon)

James asked to "run it to test". Nothing is implemented, so a throwaway script in the session
scratchpad (`live_rules_check.py`, not kept) connected via comtypes to the running Test Model
(pid 62104, ETABS 23.4.0 beta, the new seven-story file), read stories, grid tables, all areas,
frames, labels and `W_*` groups, applied the design's rules, and compared. Facts learned, now in
design section 4 and 9.1:

- `GetStories_2` returns stories **bottom-up** on ETABS 23.4 (E2K is top-down). Sort by elevation.
- Grid table key `Grid Definitions - Grid Lines` (key == name); columns Name, LineType
  (`X (Cartesian)`), ID, Ordinate, BubbleLoc, Visible. Systems in `Grid Definitions - General`
  (Name, Type, Ux, Uy, Rz, ...). **Table values follow present units**, and `UnitsString`
  changes with them (`in` -> `ft`).
- `GetAllAreas` `PointDelimiter[i]` = 0-based index of the last boundary point of area i.
  1425 areas, 5722 points, 222 frames, 44 groups (16 `W_*`).
- The four bump-outs run from grade to 47.75 ft; the main J/E walls are exposed from 46 ft up.
  Segments therefore need an optional `z_from`/`z_to`, and placement must be by largest overlap
  against the raw declared range (midpoint-with-tolerance misplaced 17 boundary shells).
- Final comparison: `W_PH` and `W_Parapet` exact; `W_Wall` rules 569 vs model 568 (+X/-X/-Y)
  and 565 (+Y); the only differences are the five pieces of the 6 in sliver column at the west
  end of J (API objects 2850/2848/2846/2844/2842), which the model loads inconsistently. Nothing
  in a model group is missing from the rules; nothing the rules leave unplaced is loaded.
- comtypes 1.4.17 is installed in `.venv` and works on Python 3.14.
- A JSON capture of the live snapshot exists only in the session scratchpad; re-capture with the
  real CLI during implementation.
